# PPE Worker Safety Detection System

[![Tests](https://github.com/Abdelrahman-cs19/ppe-safety-detection/actions/workflows/tests.yml/badge.svg)](https://github.com/Abdelrahman-cs19/ppe-safety-detection/actions/workflows/tests.yml)

![YOLOv8](https://img.shields.io/badge/model-YOLOv8-orange)
![License](https://img.shields.io/badge/license-MIT-green)

A real-time computer vision system that detects workers on camera, tracks
them persistently, checks whether each one is wearing required PPE
(helmet, safety vest, gloves, safety glasses), confirms violations over
several frames to cut false alarms, logs them to a database with a
screenshot, and surfaces everything on a Streamlit dashboard with
Telegram alerts.

Pipeline: `Video/Webcam → YOLO Detection → ByteTrack Tracking → PPE
Association → Safety Rules → Violation Logging → Dashboard/Alerts`

This README documents progress through **Milestone 2** (real-time
detection). Later milestones will extend this same file section by
section as the project grows.

## 1. Architecture

```text
ppe-safety/
├── detection/       # Milestone 2 — YOLO wrapper: load model, run inference, parse results
├── tracking/         # Milestone 3 — ByteTrack wrapper: assign/maintain persistent worker IDs
├── association/      # Milestone 4 — match PPE boxes to person boxes (IoU / center-distance)
├── rules/             # Milestone 5-6 — compliance logic + N-frame violation confirmation
├── database/         # Milestone 7 — SQLAlchemy models + repository for violations/workers
├── alerts/            # Milestone 9 — Telegram bot client, message + screenshot formatting
├── dashboard/         # Milestone 8 — Streamlit app: live view, KPIs, violation history
├── models/            # Trained YOLO weights (.pt) — git-ignored, regenerated by training
├── data/
│   ├── raw/            # Downloaded dataset(s) in YOLO format (images/ + labels/)
│   ├── processed/     # SQLite DB file lives here once Milestone 7 lands
│   └── data.yaml       # Ultralytics dataset config (classes + split paths)
├── config/            # config.py — every tunable value, one place, typed dataclasses
├── utils/             # Shared helpers — currently just the logging setup
├── scripts/           # One-off CLI entry points: train.py, evaluate.py (this milestone)
├── tests/             # pytest unit tests, one file per package
└── main.py            # Milestone 2+ — wires the whole pipeline together
```

Design principles this scaffold follows, and that the rest of the
project will keep following:

- **Config lives in one place.** `config/config.py` defines typed
  `dataclass` groups (`DetectionConfig`, `TrackingConfig`,
  `RuleEngineConfig`, ...) instead of magic numbers scattered across
  files. Every later module imports from `settings`.
- **Logging, not print().** `utils/logger.get_logger(__name__)` gives
  every module a properly namespaced, timestamped logger writing to
  both console and a rotating file under `logs/`.
- **Class order is a single source of truth.** `CLASS_NAMES` in
  `config.py` must match the `names:` block in `data/data.yaml` exactly
  — a test (`tests/test_config.py`) checks internal consistency, but
  *you* are responsible for keeping the YAML in sync after labeling.
- **Scripts vs. packages.** Anything runnable from the CLI goes in
  `scripts/` and imports logic from the real packages — it doesn't
  contain business logic itself. This keeps `detection/`, `rules/`,
  etc. independently unit-testable later.

## 2. Dataset recommendation

Your target classes are **person, helmet, safety_vest, gloves,
safety_glasses**. No single widely-used public dataset covers all five
well — most construction-PPE datasets are strong on person/helmet/vest
but weak or missing on gloves and glasses. Plan on combining sources:

| Source | Good for | Notes |
|---|---|---|
| **Roboflow Universe** — search "construction site safety", "PPE detection", "hard hat detection" | person, helmet, vest (and often "NO-helmet"/"NO-vest" negative classes) | Largest and easiest option: pick a dataset, export it in **YOLOv8** format, and you get an `images/`+`labels/` folder and a ready `data.yaml` directly. Several community datasets already merge multiple sources. |
| **Kaggle — "Hard Hat Workers Dataset"** | person, helmet | Good supplemental helmet data; originally VOC/XML — needs conversion to YOLO `.txt` (Roboflow can do this conversion for you if you re-upload it there). |
| **Academic PPE datasets with gloves/glasses** (e.g. search for "SH17" or similar recent human-safety-PPE papers on Papers-with-Code / GitHub) | gloves, safety_glasses | These classes are the hard part. Availability and licenses change, so search Papers-with-Code / GitHub / Roboflow Universe directly for the current best option rather than trusting a single hardcoded link — verify the license allows your use case before training. |
| **Self-annotated top-up set** | gloves, safety_glasses | If public data for these two classes is thin, annotate a few hundred extra images yourself (Roboflow's annotate tool or CVAT/LabelImg) and merge them in. Even 300-500 well-chosen images per rare class meaningfully helps. |

**Practical recommendation:** start with one solid Roboflow Universe
"construction PPE" dataset for person/helmet/vest, get the pipeline
working end-to-end with those 3 classes first, then extend to 5 classes
once gloves/glasses data is merged in. This matches "build
incrementally" — you don't need all 5 classes perfectly labeled before
Milestone 2.

**Merging datasets in YOLO format:** since every YOLO dataset is just
`images/` + `labels/*.txt` with integer class IDs, merging two datasets
means: (1) remap each dataset's class IDs to your unified `CLASS_NAMES`
order in `config/config.py`, (2) copy images into `data/raw/ppe_dataset/images/{train,val}`,
(3) copy the remapped label files into the matching `labels/{train,val}`
folder, keeping identical filenames (`img001.jpg` ↔ `img001.txt`). A
small remap script is easy to add once you've picked your sources — say
the word and we'll write one in the next step.

## 3. YOLO model choice

Use **Ultralytics YOLOv8** (the `ultralytics` package also supports
YOLO11 with the same API — swap `yolov8s.pt` for `yolo11s.pt` if you
want to try the newer architecture later; nothing else in this repo
changes).

Recommended starting checkpoint: **`yolov8s.pt`** (small).

- `yolov8n.pt` (nano) — fastest, best for real-time on CPU or modest
  GPUs / edge devices, but weaker on small objects like gloves/glasses.
- `yolov8s.pt` (small) — **good default for this project**: real-time
  on a mid-range GPU (and usable on CPU at a lower resolution), noticeably
  better accuracy than nano on small/partially-occluded PPE items.
- `yolov8m.pt`/`l.pt` — better accuracy still, but too slow for
  real-time webcam inference unless you have a strong GPU; more useful
  as an accuracy ceiling to compare against in your evaluation section.

For the portfolio write-up, training both `n` and `s` and reporting the
speed/accuracy trade-off (FPS vs. mAP50-95) is a nice touch — it shows
you understand the deployment trade-off, not just "I ran YOLO once."

We use **transfer learning** (fine-tuning a COCO-pretrained checkpoint)
rather than training from scratch — with a dataset in the thousands-of-images
range, this converges much faster and generalizes better.

## 4. Environment setup

```bash
# 1. Create and activate a virtual environment
python -m venv .venv
source .venv/bin/activate        # Windows: .venv\Scripts\activate

# 2. Install dependencies
pip install -r requirements.txt

# 3. (GPU users only) verify PyTorch sees your CUDA device
python -c "import torch; print(torch.cuda.is_available(), torch.cuda.get_device_name(0) if torch.cuda.is_available() else 'no GPU')"

# 4. Copy the env template and adjust if needed (device, log level)
cp .env.example .env
```

If `torch.cuda.is_available()` is `False` on a machine you expect to
have a GPU, you likely installed the CPU-only PyTorch wheel — check
[pytorch.org/get-started/locally](https://pytorch.org/get-started/locally)
for the correct install command for your CUDA version, then
`pip install torch torchvision --force-reinstall` with that command
before re-installing the rest of `requirements.txt`.

## 5. Milestone 1 — Dataset + YOLO training

**Step 1 — Get the dataset into place.** Export your chosen Roboflow
dataset (or your merged dataset) in **YOLOv8** format and place it so
the structure matches:

```text
data/raw/ppe_dataset/
├── images/{train,val,test}/*.jpg
└── labels/{train,val,test}/*.txt
```

**Step 2 — Point `data/data.yaml` at it.** The template already
created at `data/data.yaml` has `path: raw/ppe_dataset` and the 5-class
`names:` block matching `config.config.CLASS_NAMES` — edit only if your
folder name or class order differs. If your source dataset uses
different class IDs, remap them (see the merging note above) rather
than editing `names:` to match the source — keep `config.py` as the
single source of truth.

**Step 3 — Train.**

```bash
python -m scripts.train --model yolov8s.pt --epochs 100 --batch 16 --device 0
# CPU-only machine:
python -m scripts.train --model yolov8s.pt --epochs 100 --batch 8 --device cpu --imgsz 512
```

This fine-tunes the COCO-pretrained checkpoint on your PPE dataset,
writes all training artifacts (weights, curves, sample batches) to
`runs/train/ppe_yolo_v1/`, and copies the best checkpoint to
`models/ppe_yolo.pt` — the path `DetectionConfig.model_path` already
points at, so Milestone 2 needs zero config changes to pick it up.

**Step 4 — Evaluate.**

```bash
python -m scripts.evaluate --weights models/ppe_yolo.pt --split val
```

This runs Ultralytics' built-in validation and logs:

- **Precision**, **Recall** (mean, and per-class AP50 breakdown)
- **mAP50** and **mAP50-95**
- Saves a **confusion matrix** image and PR curves to
  `runs/val/ppe_yolo_eval/` (`confusion_matrix.png`, `PR_curve.png`, etc.)

Screenshot `confusion_matrix.png` and the metrics log output for your
portfolio README/case study later — this is your "here's proof the
model works" evidence, and per-class AP50 will show you immediately if
gloves/safety_glasses need more training data.

**Step 5 — Sanity-check the scaffold.**

```bash
pytest tests/test_config.py -v
```

This doesn't touch the model — it just confirms `config.py` is
internally consistent (class list matches IDs, required PPE items are
real classes, settings load without error) before you build on top of
it.

## Milestone 2 — Real-time detection

**What was added:**

- **`detection/schemas.py`** — a typed `Detection` dataclass (class name,
  confidence, box coordinates, plus `.center`, `.width`, `.height`,
  `.area` helpers). Every later module (tracking, association, rules)
  works with `Detection` objects, not raw Ultralytics results — this
  keeps them independently testable and insulates the rest of the
  pipeline from any Ultralytics API changes.
- **`detection/detector.py`** — `PPEDetector`, a thin class wrapping
  `ultralytics.YOLO`. Loads `models/ppe_yolo.pt` (fails loudly with a
  clear `ModelLoadError` if it's missing — no silent fallback), and
  exposes `.predict(frame) -> (list[Detection], InferenceStats)`.
  `InferenceStats` carries preprocess/inference/postprocess timing in ms
  and an `.fps` property, sourced directly from Ultralytics' own timing
  rather than re-measured — matches what `scripts/evaluate.py` reported.
- **`scripts/webcam_demo.py`** — opens a webcam or video file with
  OpenCV, runs `PPEDetector` per frame, draws color-coded boxes
  (violation classes in red, PPE-present/person in green/blue), and
  overlays a smoothed FPS + inference-latency readout in the corner.

**Run it:**

```bash
python -m scripts.webcam_demo                 # default webcam (index 0)
python -m scripts.webcam_demo --source 1       # a different camera
python -m scripts.webcam_demo --source clip.mp4  # a video file instead
```

Press `q` in the video window to quit.

**What to check:**

- FPS shown on-screen should be in the same ballpark as
  `scripts/evaluate.py`'s reported inference time (a GTX 1650 at
  ~16ms/frame inference should comfortably clear 30+ FPS end-to-end,
  webcam capture overhead included).
- Boxes should appear on real people/helmets/vests with reasonable
  confidence — if you deliberately don't wear a helmet on camera, a red
  `no-helmet` box should show up.
- If detections look flaky/low-confidence in your actual room lighting
  vs. the training images, that's useful signal for later — construction
  PPE datasets are usually outdoor/warehouse lighting, so a dim home
  office can genuinely perform worse than the validation numbers
  suggested. Not a bug, just a domain-shift reality worth noting in your
  portfolio write-up.

**Sanity test (no camera/model needed):**

```bash
pytest tests/test_detection_schemas.py -v
```

## Testing against a reference model

To sanity-check the custom-trained model against an independently
trained one (not part of the required pipeline, purely a benchmark):

```bash
pip install huggingface_hub
python -m scripts.download_reference_model      # saves models/reference_ppe.pt
python -m scripts.compare_models --source 0      # side-by-side live comparison
```

This opens one window split in half: your model's detections on the
left, the reference model's on the right, running on identical frames
at the same time. Note the reference model uses its own class
names/casing, so exact label text may differ - this is a visual
sanity check, not a formal apples-to-apples metric comparison (the two
models weren't trained or evaluated on the same dataset).
